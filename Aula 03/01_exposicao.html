O que é TDD?

TDD é uma técnica onde o teste é escrito antes do código de produção. O ciclo tem 3 fases: Red (escreva o teste que falha), Green (escreva o mínimo de código para passar), Refactor (melhore sem quebrar). Cada ciclo dura minutos, não horas.

Red — o teste que falha

Escreva exatamente um teste. Execute — ele DEVE falhar com um erro claro. Se o teste passou sem código, ele está testando algo errado. A falha confirma que o teste está realmente verificando comportamento ausente.

// Red: FizzBuzz — teste escrito, classe não existe @Test void retornaFizz_QuandoMultiploDe3() { assertEquals("Fizz", FizzBuzz.converter(3)); } // Resultado: ClassNotFoundException — RED ✓

Green — código mínimo para passar

Escreva APENAS o código necessário para o teste passar. Não adicione funcionalidade extra. O objetivo é o verde rápido, não a solução perfeita. Soluções absurdas são aceitáveis no Green — o Refactor vai corrigir.

// Green: implementação mínima public class FizzBuzz { public static String converter(int n) { if (n % 3 == 0) return "Fizz"; return String.valueOf(n); } } // Resultado: PASSED — GREEN ✓

Refactor — melhorar sem quebrar

Com o teste verde, melhore o código com segurança. Extraia métodos, renomeie variáveis, elimine duplicações. Execute os testes depois de cada mudança. Se quebrarem, desfaça e refatore em passos menores.

// Refactor: extrair método privado public class FizzBuzz { public static String converter(int n) { return gerarTexto(n % 3 == 0, n % 5 == 0, n); } private static String gerarTexto( boolean fiz, boolean buz, int n) { if (fiz && buz) return "FizzBuzz"; if (fiz) return "Fizz"; if (buz) return "Buzz"; return String.valueOf(n); } }

Baby Steps — passos pequenos

Cada ciclo TDD deve durar no máximo 2-3 minutos. Se o ciclo demorar mais, o passo é grande demais — quebre em sub-problemas. Baby steps evitam ficar preso em design e revelam o design emergente naturalmente.

Design emergente

Com TDD, o design do código emerge dos testes, não de um plano pré-concebido. Os testes guiam para código simples, com baixo acoplamento e alta coesão. Você descobre as abstrações certas ao escrever os testes.

Kata TDD — praticar é essencial

Katas são problemas pequenos para praticar TDD repetidamente até virar hábito. Exemplos: FizzBuzz, Roman Numerals, String Calculator, Bowling Game. O mesmo kata feito 10 vezes é mais valioso que 10 katas diferentes feitos uma vez.

Documentar o ciclo com commits

Cada fase do ciclo TDD deve ser um commit: "test: [Red] FizzBuzz retorna Fizz para múltiplo de 3", "feat: [Green] implementar regra Fizz", "refactor: [Refactor] extrair gerarTexto()". O histórico conta a história do desenvolvimento.
