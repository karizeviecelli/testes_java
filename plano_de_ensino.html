🧪 JUnit 5 & Primeiro Teste

Configure o ambiente, escreva seu primeiro @Test e entenda a pirâmide de testes que vai guiar todo o curso. A base de tudo que vem depois.

⏱️ 4 horas ☕ Maven + JUnit 5 🎯 Introdutório
💡O que você vai aprender▼
  • Por que testes automatizados existem: custo de bug em prod vs. dev
  • Configurar junit-jupiter no pom.xml e rodar mvn test
  • Anotações essenciais: @Test, @BeforeEach, @AfterEach, @BeforeAll
  • Padrão Arrange-Act-Assert (AAA): organizar cada teste em 3 fases claras
  • Assertions: assertEquals, assertTrue, assertFalse, assertNotNull
  • Nomenclatura de testes: deveRetornarX_QuandoY()
  • Executar testes na IDE (IntelliJ) e interpretar o relatório de resultados
📋Roteiro da Aula (4h)▼
  1. 1Exposição — 40 min: pirâmide de testes, custo de bugs por fase, panorama do curso completo.
  2. 2Demonstração ao vivo — 45 min: criar projeto Maven do zero, adicionar JUnit 5, escrever e rodar os 5 primeiros testes.
  3. 3Prática guiada — 70 min: alunos replicam a Calculadora com @BeforeEach e todas as assertions.
  4. 4Desafio autônomo — 45 min: suíte para a classe BancoConta.
  5. 5Code review coletivo — 20 min: 3 alunos exibem os testes; turma discute nomenclatura e AAA.

📊 Assertions Avançadas & @ParameterizedTest

Elimine duplicação de testes com @ParameterizedTest e escreva assertions expressivas que explicam a falha com clareza.

⏱️ 4 horas☕ JUnit 5 Jupiter🎯 Básico
💡O que você vai aprender▼
  • assertThrows(Excecao.class, () -> codigo()) — verificar que exceção é lançada
  • assertAll("grupo", () -> ..., () -> ...) — verificar múltiplas condições de uma vez
  • @ParameterizedTest com @ValueSource, @CsvSource e @MethodSource
  • @DisplayName — nomes legíveis nos relatórios de CI
  • Eliminar duplicação: substituir 5 @Test idênticos por 1 @ParameterizedTest
  • Boas práticas: mensagem de falha em assertions críticas
📋Roteiro da Aula (4h)▼
  1. 1Revisão rápida — 15 min: revisitar os testes da Aula 01 e identificar código duplicado.
  2. 2Exposição — 35 min: assertThrows, assertAll e a sintaxe de @ParameterizedTest.

  4. 4Prática guiada — 70 min: suíte parametrizada para MathUtils com 5+ casos por operação.

  • Kata FizzBuzz completo documentado por commits

☢️ Mutation Testing com PIT

100% de cobertura não garante qualidade. O PIT injeta bugs reais no seu código e verifica se seus testes os detectam — o mutation score revela a verdade.

⏱️ 4 horas☢️ PIT 1.15+🎯 Avançado
💡O que você vai aprender▼
  • O problema: 100% de line coverage com assertions inúteis
  • O que é um mutante: Conditional Boundary, Negate, Return Values, Void Calls
  • Mutation score = mortos/total × 100 — meta: ≥ 75%
  • Configurar pitest-maven com pitest-junit5-plugin
  • Rodar mvn pitest:mutationCoverage e ler o relatório HTML
  • Matar mutantes sobreviventes: escrever testes de boundary (7.0 vs 7.01)
  • Configurar mutationThreshold para falhar o build

📉 Gatling — Testes de Carga

Descubra onde o sistema quebra antes que os usuários reais encontrem. Gatling simula centenas de usuários e gera relatórios HTML detalhados com métricas p95 e p99.

⏱️ 4 horas📉 Gatling 3🎯 Avançado
💡O que você vai aprender▼
  • Load test, stress test, soak test, spike test — quando usar cada um
  • Estrutura de uma Simulation: scenario, exec, pause
  • Ramp-up: rampUsers(100).during(30)
  • Assertions: global.responseTime.percentile3.lt(500) (p95 < 500ms)
  • Feeders CSV: injetar dados dinâmicos nos requests
  • Relatório HTML: throughput, latência, erros por endpoint
🎯

🏛️ ArchUnit — Testes de Arquitetura

Escreva as regras de arquitetura como código Java e execute no CI. Ninguém mais vai importar Repository direto no Controller sem que o build quebre.

⏱️ 4 horas🏛️ ArchUnit 1.3🎯 Avançado
💡O que você vai aprender▼
  • layeredArchitecture(): Controller → Service → Repository — sem pular camadas
  • Controllers não acessam Repository diretamente
  • Entidades JPA não usam @Autowired
  • Naming conventions: classes em service/ devem terminar em Service
  • Dependências proibidas: pacote legacy não pode ser importado em novos pacotes
  • Integrar ao CI: ArchUnit falha o build em violações
🎯

Desafio — 5 Regras de Arquitetura em ArchUnit

Escreva testes que garantem a arquitetura do projeto e integre ao CI.

  • Regra de camadas: Controller → Service → Repository
  • Controllers não importam nada de repository/
  • Classes em service/ devem ter nome terminando em Service
  • Entidades não têm @Autowired
  • Build falha ao introduzir violação intencional
📦 EntregaClasse ArchUnitTest + print do build falhando ao violar uma regra.
✓ Regra de camadas
✓ Naming convention
✓ Dependência proibida
